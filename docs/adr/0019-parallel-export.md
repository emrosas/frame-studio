# 0019: Long MP4 exports split across render workers, muxed in the studio server

Status: accepted, 2026-11-10 (`.scratch/export-speed/issues/02-parallel-export.md`). Amends ADR 0008's render worker and its "exports encode in the page that draws the frames".

## Context

Promotional videos will run 10 to 15 minutes. One render worker takes about 57 to 75 ms a 1080p frame through the whole pipeline, most of it Chromium's CPU raster and our RGBA to I420 conversion, so a 15 minute video at 30 fps takes 25 minutes or more on an M1 Pro (`.scratch/export-speed/research/benchmark.md`). The pool ran one worker taking one job at a time, which left most cores idle. A frame is a pure function of (scene, frame, fps), so nothing stops several pages drawing different frames of one export at once. Two things needed deciding: where the pieces become one file, and how to keep that file the same as the one a single page makes.

## Decision

- **Helper workers on slots.** The render pool keeps several worker pages, each on a slot: 0 is the worker every server has, and 1 and up are helpers. A page connects with `render.html?worker=<slot>`, a page on a taken slot replaces the one there and takes over its job, and every job goes to whichever worker is free. An export leases helpers for its length; they close 30 seconds after the last lease ends, so back-to-back exports reuse them. A server without the app asks its Electron worker process for helper windows over the stdin it already uses; in the app, the server asks main, which opens hidden windows like the main worker's. Each window is its own renderer process, so they draw in parallel. Each helper also gets an in-memory session of its own: Chromium allows six connections to a host per session, and every worker page keeps one open for its jobs, so six workers in one session left no connection for their writes and the export hung.
- **Segments on key frames.** `splitRange` cuts the range into runs of whole key-frame intervals, counted from the export's first frame as the serial export counts them. Segments shrink as the range runs out (each takes about half of what is left divided among the workers), so workers finish close together instead of one drawing the last long segment alone. Exports under 10 seconds, GIFs, and `--workers 1` take the single-page path.
- **A fresh encoder at every key frame, on both paths.** VideoToolbox's rate control carries state across key frames, so a segment encoded by a new encoder came out different from the same frames in the serial file (the first interval matched byte for byte, the rest didn't). Now `encodeVideo` starts a new encoder at each key frame in both paths. An interval's packets then depend only on its frames, and a parallel file decodes to the same frames as the serial one, with the same packets. Two things differ between any two exports, serial ones included: Mediabunny's creation times in `mvhd` and `tkhd`, and two bytes in the user-data SEI that VideoToolbox puts before each key frame, which no decoder reads. Every encoder must write the same avcC, which both paths check.
- **The server muxes.** Each worker writes its segment's packets to a temporary file through the existing sinks, as length-prefixed records (`src/export/packets.ts`) with integer microsecond timestamps. The studio server reads each segment back once every segment before it is in, and feeds it to `Mp4Muxer` (`src/export/mp4-mux.ts`), the same muxer the page uses, now split out of `mp4.ts` and free of browser APIs. One coordinating page was the other option, but it would need the segments sent back down to it, could not draw while it muxed, and would put a long-lived job in front of the queue. Mediabunny runs in Node unchanged.
- **Sound once.** One job renders the scene's audio offline and encodes it, as ADR 0005 has it, and writes the packets as records; the server rebuilds them with the timestamps the page would have used. The colour space the frames carried and the AAC edit list and roll group come from the shared muxer and `finishAudioTrack`, so they're unchanged.
- **Worker count.** By default one per core less one, at most one per 1.5 GB of memory less one, between 1 and 4. The cap is 4 because the benchmark gained little past 4 or 5 workers on an M1 Pro, while per-frame encode time rose (one hardware encoder). `FRAME_STUDIO_EXPORT_WORKERS` and the CLI's `--workers` override it.
- **Progress and cancel.** Progress sums the frames done across segments. A cancel aborts every job, waits for them to stop, and removes the temporary files and the partial output.
- **A stall stops the export.** If no job reports progress for two minutes, the export cancels with an error that suggests one worker, instead of waiting forever.
- **No App Nap.** A worker process with no visible window is an App Nap candidate. The worker-only process holds a `prevent-app-suspension` blocker; the app holds one while helpers are open.

## Consequences

- Restarting the encoder costs a flush and a new VideoToolbox session every 2 seconds of video, which the benchmark doesn't show above noise, and rate control starts over on each interval, which costs a little quality at the start of each one. The serial file changed bytes with this, though not its frame count, timing or colour.
- Exports now produce the same frames and packets whatever the worker count, which the browser test checks with ffmpeg (dropping SEI units before hashing packets). That holds on one machine and one Electron build; a different VideoToolbox could encode differently, as ADR 0005 says for audio.
- Helpers cost memory: a renderer process each, 175 to 325 MB at 1080x1920, and about 2 GB for the whole Electron process with 7 workers. The default's 1.5 GB a worker leaves plenty of room.
- The parallel path moves bytes through the server twice (worker to temporary file, file to muxer), at most the size of the video, which is small next to drawing time.
- Speedup is well under linear: per-frame raster and conversion cost rises with more workers on the same chip. `benchmark.md` has the numbers.
- ADR 0008 still holds in shape: one server, render workers that are pages taking jobs, Electron's Chromium as the pixel reference. What changed is that there can be more than one worker, and that a long MP4 is muxed in the server instead of the page.
