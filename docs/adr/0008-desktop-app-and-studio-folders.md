# 0008: The desktop app works on studio folders, through one studio server

Status: accepted, 2026-09-26 (ticket 19). Amends ADR 0001.

## Context

M10 ships the studio as an Electron app (ADR 0001). The studio has assumed the repo so far: scenes in `scenes/`, projects in `projects/`, rigs in `src/rigs/`, and Vite loading all of them, TypeScript included. An installed app has no repo and no Vite dev server, but agents still write drawing code while it runs. The Node tools render through Playwright's Chrome for Testing, which an app can't ship, and the user wants exports and agents to work without a terminal. Research: `.scratch/frame-studio/research/t3code-desktop.md` and `.scratch/frame-studio/research/runtime-rig-loading.md`.

## Decision

- **Studio folders.** The app opens a folder the user picks. It holds `scenes/`, `projects/`, `rigs/` and `audio/` (rigs and generators for every scene in the folder), `references/`, `out/` and `.frame-studio/`. The built-in rigs and generators ship inside the app as read-only source files. The repo opens as a studio folder too, with `src/` as its built-ins. One folder is open at a time. File › Open Folder switches, and the app reopens the last one. The first launch offers New studio folder, which creates `~/Frame Studio/` with `hello` and a copy of `bears-story`, or Open folder.
- **Changing a built-in.** A studio folder never replaces a built-in. An agent makes a variant (`bear.blush`) or a new rig in `rigs/`, and an id that clashes with a built-in is an error, as in ADR 0007.
- **One studio server.** A standalone Node server holds everything that needs the machine. It serves the built viewer itself, so the page, its API and its rig modules share one origin. It tries a fixed port first so the page's storage survives restarts, and falls back to any free port. The page talks to it over HTTP, and the server pushes the queue, turn events, library changes and export progress over one Server-Sent Events stream, where ADR 0001 said WebSocket. Every push is one-way, and an event stream needs no library.
- **Pairing.** Whoever starts the server gives it a token. The page trades the token once for an HttpOnly, SameSite=Strict cookie. Tools send it as a bearer token. The app hands the token to the page through its preload. `npm run dev` prints the viewer URL with the token in the fragment, and the page pairs and removes it. The server also writes its address and token to `.frame-studio/server.json`, readable only by the user, for tools that want to reuse it. Requests from other sites are refused, as before.
- **Loading code without Vite.** A module service in the studio server serves rigs and generators to the page. Node's own type stripping turns each file into JavaScript, and every import is rewritten to a URL carrying a hash of the file and everything it imports, so an edit reloads only that file and its importers. The server loads the same files into Node with a resolve hook. HTML exports bundle with Rolldown on its own. Runtime TypeScript must be erasable: no enums, namespaces or constructor parameter properties, which typecheck enforces.
- **Import names.** Rigs and generators outside `src/` import the built-ins as `@frame-studio/rigs/...`, `@frame-studio/engine/...` and `@frame-studio/audio/...`. Every loader maps the prefix. A studio folder gets a `tsconfig.json` that maps it to the app's built-in sources, so an agent can type-check its rigs.
- **The render worker.** Agents' renders, contact sheets, hit tests and exports run in `render.html` opened as a render worker. It connects to the studio server like any page and takes jobs from it. The app opens it in a hidden window. A server started without the app launches Electron in a worker-only mode. Electron's Chromium is the pixel reference: the CLI and the pixel tests render through the worker too, and Playwright stays for driving the viewer's interface in tests.
- **Export in the viewer.** An Export button makes MP4, GIF or HTML of the scene or the selected range, with or without sound. The render worker encodes while the viewer keeps playing. Files go to `out/`, and the app offers Reveal in Finder.
- **External agents.** `tools/mcp/server.ts` becomes a stdio shim. If `.frame-studio/server.json` names a live server for the folder, it forwards every MCP message to that server's MCP endpoint. Otherwise it starts a headless server on the folder, with agents off, and forwards to that. The CLI does the same. The app ships the shim as `frame-studio-mcp`, which runs the shim on the app's own binary in Node mode.
- **Dev workflow.** `npm run dev` starts the studio server on the repo with Vite's dev middleware inside it, for the viewer's own code and its hot reload, so there's one origin as in the app. Scenes and rigs load through the server's file store and module service in dev as in the app. The dev token stays the same across restarts, in `.frame-studio/dev-token`, so a page paired once stays paired.
- **The shell.** Electron's code lives in `desktop/`, never imported by `src/`. Main runs the studio server in a `utilityProcess`, reads PATH from the user's login shell first so `claude` and `codex` are found when Finder launches the app, and keeps IPC to native features: the token handoff, folder pickers, Reveal in Finder, links and menus. The server removes `ELECTRON_RUN_AS_NODE` from everything it starts. The shell has a single-instance lock, saved window bounds, a sandboxed page, a reload after a page crash, a server restart with backoff, and logs in `~/Library/Logs/Frame Studio/`.
- **Packaging.** electron-builder builds an unsigned macOS arm64 app and DMG named Frame Studio, with bundle id `studio.frame.app`. The server, main process and shim are bundled with Rolldown into single files, so no `node_modules` ships except Rolldown's native binding. The Agent SDK's code sits inside the server bundle without its 220 MB binary, and an exclusion glob stays as a second guard. A check after each build fails if anything named `claude-agent-sdk-` is inside or the app is over 300 MB. Signing, notarization, updates, Windows and Linux come later.

## Consequences

- The Vite plugin, `import.meta.glob` scene loading and `ssrLoadModule` go away. The viewer, the render page, the tools and the tests all load scenes and code through the studio server.
- A rig edit reloads in the page without a full refresh, but every reload keeps the old modules in memory, as Vite's reloads do today. A page that has seen many edits should be reloaded now and then.
- The CLI and the pixel tests need Electron installed (`npm install` brings it) and render slightly differently from Chrome for Testing. Pixel guarantees hold within Electron.
- An agent in the app can't edit the built-in rigs; in the repo it still can, since `src/rigs` is the built-ins there.
- ADR 0001's "Electron loads the viewer and passes it the server's address" becomes "the server serves the viewer and Electron opens it". The protocol stays the one ADR 0001 describes, over an event stream instead of a WebSocket.
